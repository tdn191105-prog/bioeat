# Реальная оплата: СБП и карта

Кому: команде проекта и столовой перед переговорами о пилоте.
Состояние кода: интеграция с ЮKassa написана и покрыта тестами с замоканным HTTP
(`tests/test_payments.py`). **Реальный тестовый платёж не проводился:** ключей тестового
магазина ЮKassa в окружении разработчика не было. Как только ключи появятся, проверка займёт
полчаса (см. раздел 6).

Данные о тарифах собраны в октябре 2026 года и **меняются** — перед подписанием договора
сверьте их на сайтах провайдеров.

## 1. Главный вопрос: кто продавец

Деньги студентов должны поступать на расчётный счёт того, **кто кормит и отвечает за еду**:
столовой, комбината питания или самого вуза. Студенческая команда продавцом быть не может и
не должна: она не готовит еду, не платит налоги с выручки и не отвечает перед покупателем
по закону о защите прав потребителей. Если деньги пойдут через счёт члена команды, это
посредническая деятельность без договора и кассы, то есть прямой риск для всех.

Схема для пилота: **договор эквайринга заключает оператор питания**, команда предоставляет
сервис (приложение) по отдельному договору или безвозмездно на время пилота.

Варианты, кто может быть оператором питания в РОСБИОТЕХ (уточнить на переговорах):

| Кто кормит | Что это значит для эквайринга |
|------------|-------------------------------|
| Сторонний оператор (ООО / ИП на аутсорсе) | Самый быстрый путь: ЮKassa и банки подключают ООО и ИП онлайн |
| Комбинат питания вуза — бюджетное или автономное учреждение | Возможно, но дольше: казначейский счёт, закупка услуги эквайринга по 223-ФЗ / 44-ФЗ, согласование с бухгалтерией вуза. Нужно уточнить у провайдера: публичные тарифы ЮKassa не разделяют условия для госучреждений |
| У столовой уже есть эквайринг в банке (терминалы на кассе) | Скорее всего, тот же банк подключит интернет-эквайринг по допсоглашению — это может оказаться быстрее всего |

Самозанятые: ЮKassa подключает самозанятых, но для столовой это не подходит — оборот
общепита превысит лимит НПД (2,4 млн ₽ в год), а продажа чужих товаров самозанятым запрещена.

## 2. Сравнение провайдеров

| | ЮKassa | CloudPayments | Интернет-эквайринг банка (Т-Банк, Сбер, Альфа или банк столовой) |
|---|---|---|---|
| Кто подключается | ИП, юрлица, самозанятые ([тарифы](https://yookassa.ru/docs/support/payments/fees)) | ИП и юрлица | Клиенты банка с расчётным счётом (ИП, юрлица); бюджетные — индивидуально |
| Карты (МИР, Visa, MC) | 3,5 % на базовом тарифе (до 3 млн ₽ в месяц), **плюс НДС 22 % на комиссию с 01.01.2026** | Индивидуально по договору, публичной ставки для малого оборота нет | Индивидуально (Т-Банк публикует «индивидуально, подключение от 1 дня») |
| СБП | Есть (`payment_method_data.type = sbp`). Ставка на странице тарифов не указана, НДС на комиссию по СБП не взимается. Общие ограничения СБП для бизнеса — не выше 0,4–0,7 % в зависимости от вида деятельности (проверить) | Есть, ставка по договору | Есть; в торговом эквайринге Т-Банка СБП от 0,2 %, для интернет-эквайринга уточнять |
| Сроки подключения | Онлайн, обычно 1–3 рабочих дня после проверки сайта | От 1 дня онлайн | Для своего клиента — несколько дней, через менеджера |
| Тестовый режим без договора | **Да**: тестовый магазин в личном кабинете сразу после регистрации, тестовые карты | Да, тестовый терминал | Обычно после подачи заявки |
| Python | Официальный SDK `yookassa`; мы используем прямой HTTP через `httpx` | Только HTTP API | Только HTTP API |
| Вебхуки | Есть; проверка — по IP-адресам ЮKassa и перезапросу статуса | Есть, подпись HMAC (`Content-HMAC`) | Есть (у Т-Банка — поле `Token`) |
| Возвраты | Полные и частичные, по API; по СБП деньги возвращаются на следующий день | По API | По API |
| Чеки 54-ФЗ | Своя онлайн-касса через партнёров ЮKassa **или** сервис «Чеки от ЮKassa»; объект `receipt` в платеже | Своя касса или сервис чеков CloudKassir | Обычно своя онлайн-касса (АТОЛ Онлайн, OFD-сервисы), часть банков предлагает облачную |
| Внутри WebView | Страница оплаты работает; ссылки СБП (`https://qr.nspk.ru/…`, `bankXXXXXXXXXX://`) нужно открывать вне WebView — сделано в Android-обёртке | То же | То же |

## 3. Рекомендация

**Для пилота — ЮKassa.** Причины:

1. Тестовый магазин без договора: интеграцию можно проверить сегодня, а не после подписания.
2. Подключение онлайн за несколько дней, без визита в банк.
3. Карты и СБП одним договором, возвраты и чеки через тот же API.
4. Код уже написан (`app/payments/yookassa.py`), осталось вставить ключи.

**Если у столовой уже есть эквайринг в банке** — стоит спросить у банка про интернет-эквайринг
с СБП: комиссия по СБП у банков ниже, а договор и счёт уже есть. Интерфейс провайдера в коде
общий, банк подключается заменой одного класса (`app/payments/stubs.py` — заготовки
CloudPayments и банка с тем же интерфейсом).

Комиссия для понимания экономики: средний чек ~300 ₽ → карта 3,5 % + НДС ≈ 12,8 ₽,
СБП 0,4–0,7 % ≈ 1,2–2,1 ₽. Поэтому СБП в приложении стоит первым способом оплаты (так и сделано).

## 4. Что нужно от столовой и от команды

**От столовой (оператора питания):**

- юрлицо или ИП, ИНН, ОГРН, расчётный счёт, контакты бухгалтера;
- решение, кто подписывает договор с ЮKassa (или с банком) и чей это счёт;
- онлайн-касса или согласие на «Чеки от ЮKassa»; данные для чека:
  система налогообложения, **ставка НДС** (общепит часто на УСН «без НДС» или пользуется
  освобождением по пп. 38 п. 3 ст. 149 НК РФ — решает бухгалтерия),
  признак предмета расчёта (для готовой еды — `commodity`, «товар»);
- ответственный за возвраты и спорные платежи.

**От команды:**

- **сайт на домене** с HTTPS, где опубликованы: оферта (условия продажи, кто продавец,
  реквизиты), правила возврата, контакты, **политика обработки персональных данных
  (152-ФЗ)** и согласие на обработку; провайдер проверяет сайт при подключении;
- уведомление Роскомнадзора об обработке ПДн — подаёт оператор ПДн (тот, кто собирает
  данные студентов: вуз, столовая или команда — определить в договоре);
- публичный адрес сервера для вебхуков (`PUBLIC_BASE_URL`), см. `docs/deploy.md`.

## 5. Как устроено в коде

```
app/payments/
├── base.py          PaymentProvider: create_payment, get_status, refund, parse_webhook
├── demo.py          DemoProvider — прежнее поведение, с моделированием отказа банка
├── yookassa.py      YooKassaProvider — HTTP API v3 через httpx
├── stubs.py         CloudPayments и банк: тот же интерфейс, TODO
└── receipt.py       чек 54-ФЗ: позиции, НДС, бонусная скидка до копейки
```

Выбор провайдера — `PAYMENT_PROVIDER=demo|yookassa|cloudpayments|bank`. Если переменная
не задана, работает старый флаг: `DEMO_PAYMENTS=true` → demo, `false` → yookassa
(раньше флаг ни на что не влиял). `simulate_failure` с клиента принимается только в демо.

Поток оплаты:

1. Заказ `created` → `POST /api/orders/{id}/pay` создаёт платёж у провайдера
   с `Idempotence-Key = rospit-pay-<id нашего платежа>` — двойной клик не создаст двух платежей.
2. Клиент уходит по `confirmation_url`: карта и 3-D Secure — страница ЮKassa; СБП — выбор
   банка и переход в его приложение.
3. Банк возвращает студента на `#/order/{id}?payment=return`, экран опрашивает
   `GET /api/orders/{id}/payment-status` («Ждём подтверждения банка…»).
4. **Источник истины — вебхук** `POST /api/payments/webhook/yookassa`. Телу не доверяем:
   проверяем IP (список адресов ЮKassa) и перезапрашиваем платёж через API. Сумма и заказ
   сверяются, обработка идемпотентна, повторное уведомление ничего не меняет. Опрос статуса
   с экрана тоже перезапрашивает API, поэтому заказ оплачивается, даже если вебхук задержался.
5. Заказ становится `paid` только по подтверждённому статусу `succeeded`. Если к этому моменту
   заказ отменён, истёк, прошла отсечка перемены или он уже оплачен другим платежом —
   **автоматический возврат**.
6. Отмена оплаченного заказа вызывает `provider.refund()`; статус возврата хранится
   (`payments.refund_status / refund_ref`). Если банк возврат не принял — заказ не отменяется,
   студент видит понятную ошибку.
7. Чек: позиции заказа с названиями, количеством и ценами; бонусная скидка распределена по
   позициям так, что сумма чека совпадает с суммой платежа до копейки (строку при необходимости
   делим на две); контакт для чека — почта студента. При возврате передаётся чек возврата.

Переменные окружения (секреты — только из окружения, в `.env.example` без значений):
`PAYMENT_PROVIDER`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `PUBLIC_BASE_URL`,
`RECEIPT_ENABLED`, `RECEIPT_VAT_CODE` (1 — без НДС, 11 — НДС 22 %), `RECEIPT_PAYMENT_SUBJECT`,
`RECEIPT_TAX_SYSTEM_CODE`, `YOOKASSA_CHECK_IP`.

## 6. Как проверить с тестовым магазином ЮKassa

1. Зарегистрироваться на yookassa.ru → «Тестовый магазин» → взять `shopId` и секретный ключ.
2. Поднять сервер по HTTPS (`docs/deploy.md`, для проверки хватит временного туннеля).
3. В личном кабинете ЮKassa → «Интеграция» → «HTTP-уведомления»: адрес
   `https://<домен>/api/payments/webhook/yookassa`, события `payment.succeeded`,
   `payment.canceled`, `refund.succeeded`.
4. ```bash
   PAYMENT_PROVIDER=yookassa YOOKASSA_SHOP_ID=… YOOKASSA_SECRET_KEY=test_… \
   PUBLIC_BASE_URL=https://<домен> docker compose -f docker-compose.prod.yml up -d
   ```
5. Оформить заказ, оплатить тестовой картой из документации ЮKassa, убедиться,
   что заказ стал «Оплачен», отменить — проверить возврат в кабинете ЮKassa.
   Записать `provider_ref` платежа в отчёт.

Если тестовый магазин не поддерживает СБП (уточнить в кабинете) — СБП проверяется
на боевом магазине платежом на 1 ₽ с возвратом.
